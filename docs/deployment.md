# Deployment (M9)

MENTORX runs as three hosted pieces, all on free plans:

| Piece | Host | Defined in |
|---|---|---|
| Frontend (static React build) | Vercel | [frontend/vercel.json](../frontend/vercel.json) |
| API (FastAPI, native Python 3.12, no Docker) | Render web service `mentorx-backend` | [render.yaml](../render.yaml), [backend/scripts/start.sh](../backend/scripts/start.sh) |
| Database (PostgreSQL) | Render managed Postgres | [render.yaml](../render.yaml) |

```
browser ──HTTPS──> Vercel  ── /assets, /*  → index.html (SPA)
                     │
                     └── /api/* (rewrite, server side) ──HTTPS──> Render: mentorx-backend ──> mentorx-db
```

The browser only ever talks to the Vercel origin. Vercel forwards `/api/*` to Render, so the API is
same-origin from the browser's point of view. That's what lets the refresh token sit in a
`Secure; HttpOnly; SameSite=Strict` cookie scoped to `/api/v1/auth`.

## How Render builds and starts the API

**Build** (`buildCommand` in `render.yaml`, from the repository root):
`pip install ./ml && pip install -e ./backend`. The backend is installed in editable mode, so it
finds the trained model (`backend/model_artifacts/`) and the question bank (`question_bank/`)
relative to its own source. Python is pinned with the `PYTHON_VERSION` variable.

**Start** (`startCommand`): `cd backend && sh scripts/start.sh`, which runs on every deploy and
restart:

1. `alembic upgrade head` applies any new migrations.
2. `python scripts/seed.py` loads the question bank. It's idempotent, so running it again changes nothing. In production it loads only questions marked `review_status: reviewed` unless `SEED_INCLUDE_DRAFTS=true`.
3. `uvicorn` serves on `$PORT` with **one worker**. The rate limiters and the model cache live in process memory. Before adding workers or instances, move them to a shared store such as Redis.

## First deployment checklist

### 1. API and database (Render)

1. Render dashboard → **New → Blueprint** → pick this repository. Render reads `render.yaml` and creates `mentorx-backend` and `mentorx-db`.
2. When prompted, fill in the variables marked `sync: false`:
   - `CORS_ORIGINS`: the Vercel URL, e.g. `https://mentorx.vercel.app`. Requests normally arrive through the same-origin rewrite, so this is a second line of defence.
   - `SEED_INCLUDE_DRAFTS`: leave it **empty**. Set it to `true` only for a supervised demo while the question bank is still awaiting review. Without it, a bank with no reviewed questions leaves the subject empty.
3. `JWT_SECRET` is generated by Render. The app refuses to start in production with the dev secret or with `COOKIE_SECURE=false`.
4. Wait for the deploy. Render polls `/api/v1/health/ready`, which checks the database connection, before switching traffic. (It does not check the model: the smoke test does, by printing the model version in use).
5. Note the service URL. Render may add a suffix. **Never guess it**: copy it from the service page. (The plain `mentorx-api.onrender.com` belongs to another Render user, and pointing the rewrite at a stranger's host would send students' passwords to them.)

### 2. Frontend (Vercel)

1. Vercel → **Add New → Project** → import the repository, set **Root Directory** to `frontend`. `vercel.json` sets the framework, build and output.
2. Set the `/api/:path*` rewrite destination in `frontend/vercel.json` to your exact Render URL and commit. Then open `https://<your-app>.vercel.app/api/v1/health`: it must show `{"status":"ok"}`. Anything else means the rewrite points at the wrong server.
3. Don't set `VITE_API_URL`. Leaving it empty keeps API calls same-origin.

### 3. Smoke test production

```bash
cd backend
python scripts/smoke.py https://<your-app>.vercel.app      # through the rewrite (what users hit)
python scripts/smoke.py https://<your-render-service>.onrender.com   # the API directly
```

The script creates a throwaway account and tests whichever version is live. For v3 it onboards with a grade, reads Home, answers two placement-check questions and one practice question, reads the AI status and, when Geography is seeded, answers one map question in Geography; it prints `PASSED (v3)`. It also checks the security headers, HSTS and the refresh cookie round trip, then deletes the account. It exits non-zero on the first failure. Run it after every production deploy.

CI runs the same script in its `e2e` job ([.github/workflows/ci.yml](../.github/workflows/ci.yml)): it installs the API with Render's build command, starts it with Render's start command in production mode against PostgreSQL, and runs the smoke test. Every push to `main` is therefore checked for a working install, migrations, seeding and model loading before Render auto-deploys it.

## Mathematics content (MENTORX v2)

The Mathematics subject comes from FoundationalASSIST, which is licensed and never committed,
so a fresh database has no maths content until it is seeded once. The app then answers
`503 content_missing` on onboarding.

**Seed the production database from your own computer (recommended):**
1. Once, check which question images still load (writes `image_check.json` next to the CSVs;
   questions whose images haven't been verified are not served):
   ```
   python scripts/check_images.py --data-dir "C:/path/to/folder/with/Problems.csv"
   ```
2. Render dashboard -> `mentorx-db` -> **Connect** -> copy the **External Database URL**.
3. In a terminal on your computer, in `backend/` with the virtual environment active:
   ```
   set DATABASE_URL=<paste the external URL>        (PowerShell: $env:DATABASE_URL="<url>")
   python scripts/seed_math.py --data-dir "C:/path/to/folder/with/Problems.csv"
   ```
4. It prints the number of skills, usable questions (single-skill and mixed), whether images
   were checked, prerequisite links and resources. It's safe to run again: admin edits are kept.

Images are not copied: verified images load from the dataset's own HTTPS hosts, which the
frontend's Content-Security-Policy (`frontend/vercel.json`, `img-src`) allows explicitly.

Alternatively, if the CSVs are available on the server, set `MATH_DATA_DIR`; `scripts/start.sh`
then refreshes the content on every start.

The model files (`backend/model_artifacts/foundationalassist/`, about 7 MB) are committed and
served with NumPy, so the API needs no PyTorch. `GET /api/v1/health/model` reports whether the
model loaded. If it didn't, the app shows observed performance only and never labels anything
as a model prediction.

Admins: set `ADMIN_EMAILS` to give accounts the Content admin page (it also has the live
Model monitor and the AI tutor texts).

## Geography content (v3, optional)

Geography map skills come from the Slepemapy.cz 2015 dataset (ODbL; see
`docs/modules/geography.md`). The CSVs are never committed. Seed after the v3 deploy (the
migration must have run):
```
python scripts/seed_geography.py --data-dir "C:/Users/Tanish Gupta/Downloads/mentorx-new-subject/slepemapy-2015-05-21"
```
Until it runs, Geography is invisible and the app is Maths only. Seeding Maths again never hides
Geography (and vice versa). The Geography model files are in `backend/model_artifacts/geography/`
(`KT_SUBJECTS`).

## Regrading old answers after the v3 answer-checking change

v3 accepts correctly rounded decimals, recovered fractions, units, "$" and so on (see
`docs/modules/tutor.md`, "Answer checking"). Answers given before v3 can be re-checked once:
```
python scripts/regrade.py --dry-run     # shows what would change; changes nothing
python scripts/regrade.py               # applies it (safe to run again)
```
It only turns wrong into right, records `regraded_at` on each changed answer, hides the cached AI
explanations of those answers, and rebuilds the affected students' skill states and
recommendations. It prints question and answer ids, never who answered.

## AI tutor (optional)

Set `OPENROUTER_API_KEY` on the API service to switch on AI explanations and AI hints (free
OpenRouter models; leave it empty to switch the feature off and hide its buttons). Paste the key
alone: quotes, spaces and a "Bearer " prefix are removed, but nothing else is fixed. The default
model chain is in `app/core/config.py` (`AI_MODEL`, `AI_FALLBACK_MODELS`); if those variables
exist on Render from an older version, delete them so the new defaults apply.
`AI_TOTAL_SECONDS` (default 50, max 90) caps one AI request across all models. `AI_DAILY_LIMIT`
caps new AI texts per student per day (reset at the student's midnight).

Check it: Admin → **Test AI** (`POST /api/v2/admin/ai/test`) shows OK with the model and the time
taken, or the error. If OpenRouter rejects the key, the log says "OpenRouter rejected the API key
(status 401)", `GET /api/v2/ai/status` reports `key_ok: false`, and the AI buttons hide for 10
minutes (or until a successful Test AI). Free models may log prompts: only the question, its answer
and the student's response are sent, never a name, email or id.

## Keeping the free server awake (optional)

Render's free API sleeps after about 15 idle minutes, and the first request then takes up to
about a minute (83.9 s measured on 2026-11-13), which can also make the first AI request time out.
A free cron service can ping it: at https://cron-job.org create a job for
`https://mentorx-backend-uco2.onrender.com/api/v1/health` every 10 minutes. Render's free plan has
750 instance hours a month, enough for one always-on service.

## Environment variables

| Variable | Production value | Notes |
|---|---|---|
| `ENVIRONMENT` | `production` | Turns on the production checks, HSTS and reviewed-only seeding, and turns off `/docs` |
| `DATABASE_URL` | from `mentorx-db` | `postgres://` URLs are rewritten to the psycopg driver automatically (Render, Neon) |
| `JWT_SECRET` | generated | 32+ random characters |
| `COOKIE_SECURE` | `true` | Required in production |
| `COOKIE_SAMESITE` | `strict` | Works because of the same-origin rewrite |
| `CORS_ORIGINS` | Vercel URL | Comma-separated |
| `SEED_INCLUDE_DRAFTS` | unset | See above |
| `PILOT_ACTIVE` | `false` | `true` while pilot sign-ups are open ([pilot guide](modules/pilot.md)) |
| `POSTTEST_OPEN` | `false` | `true` at the end of the pilot |
| `ADMIN_EMAILS` | your team's emails | Comma-separated; these accounts see the Study page and exports |
| `LOG_LEVEL` | `INFO` | JSON logs with a request ID per request (the `X-Request-ID` header) |
| `LOGIN_ATTEMPTS_PER_MINUTE` | `5` | Per account |
| `REGISTRATIONS_PER_HOUR` | `10` | Per client IP |
| `EXPOSE_DOCS` | unset | `true` re-enables `/docs` in production |
| `OPENROUTER_API_KEY` | your OpenRouter key | Empty = AI tutor off. Paste the key only |
| `AI_MODEL`, `AI_FALLBACK_MODELS` | unset | Defaults in `config.py`; delete old values |
| `AI_TOTAL_SECONDS` | unset (50) | Time budget for one AI request (max 90) |
| `AI_DAILY_LIMIT` | unset (40) | New AI texts per student per day |
| `KT_SUBJECTS` | unset | Default `GEO=model_artifacts/geography`; Maths uses `KT_ARTIFACTS_DIR` |

## Hardening in place

- **Security headers**: on every API response (`nosniff`, `DENY` framing, `no-referrer`, a deny-all CSP, `Cache-Control: no-store` on `/api/*`, and HSTS in production), and on the frontend through `vercel.json` (a strict CSP with no inline scripts and no third-party origins).
- **Rate limits**: login attempts per account, and registrations per client IP (HTTP 429 with `Retry-After`).
- **Production config validation**: the app won't boot with the dev JWT secret or insecure cookies.
- **Smaller attack surface**: no interactive docs or OpenAPI schema in production, and no `Server` header.
- **Error pages**: the frontend has a not-found route and an error boundary, and the API returns structured JSON errors with a request ID.

## Known limitations of the free plans

- **Cold starts.** Render's free web service sleeps after about 15 minutes idle, and the first request then takes up to about a minute. Vercel's rewrite may time out on that request, and a retry succeeds. Before a demo or a pilot session, open `/api/v1/health` first, or move to a paid instance.
- **Free Postgres expiry.** Render's free databases expire after a limited period (check the current Render terms). Before the pilot (M11), either upgrade the database or point `DATABASE_URL` at another managed Postgres such as Neon. The URL is normalised either way. Back up first with `pg_dump`.
- **Client IP for the registration limit.** Uvicorn trusts `X-Forwarded-For` from any proxy (`FORWARDED_ALLOW_IPS=*`), because Render's proxy addresses aren't fixed. A client calling Render directly could spoof that header to get around the per-IP sign-up limit. The per-account login limit doesn't depend on IP. This is acceptable for the pilot's scale. Revisit it with a shared limiter store.
- **Single instance.** See "How Render builds and starts the API".

## Load testing (NFR-PERF-01)

```bash
cd backend
REGISTRATIONS_PER_HOUR=1000 uvicorn app.main:app --port 8000
python scripts/loadtest.py http://127.0.0.1:8000 --users 50 --questions 20
```

The target is p95 ≤ 300 ms for *next question* and *submit answer*. Run it against a local server or a staging copy, not the production database.

## Moving from the old Docker service (November 2026, one time)

Until M12 the API ran as a Docker service called `mentorx-api`. Rather than converting that
existing service from Docker to native Python in place, `render.yaml` now defines a new service,
`mentorx-backend`, that uses the same database (`mentorx-db`, so no data is lost).

1. Render dashboard → **Blueprints** → the MENTORX blueprint → **Manual sync** (or wait for
   the automatic sync). Render creates `mentorx-backend`.
2. Fill in its `sync: false` variables as for the first deployment: `CORS_ORIGINS`,
   `ADMIN_EMAILS`, and leave `SEED_INCLUDE_DRAFTS` empty.
3. Wait until it shows **Live**, then copy its URL.
4. Point `frontend/vercel.json`'s `/api/:path*` rewrite at that URL, commit and push, and run the
   smoke test against the Vercel site.
5. Delete the old `mentorx-api` service (Settings → Delete Web Service).

`JWT_SECRET` is newly generated for the new service, so everyone has to log in once more.
