# Deployment (M9)

MENTORX runs as three hosted pieces, all on free plans:

| Piece | Host | Defined in |
|---|---|---|
| Frontend (static React build) | Vercel | [frontend/vercel.json](../frontend/vercel.json) |
| API (FastAPI in Docker) | Render web service | [backend/Dockerfile](../backend/Dockerfile), [render.yaml](../render.yaml) |
| Database (PostgreSQL) | Render managed Postgres | [render.yaml](../render.yaml) |

```
browser ──HTTPS──> Vercel  ── /assets, /*  → index.html (SPA)
                     │
                     └── /api/* (rewrite, server side) ──HTTPS──> Render: mentorx-api ──> mentorx-db
```

The browser only ever talks to the Vercel origin. Vercel forwards `/api/*` to Render, so the API is
same-origin from the browser's point of view. That's what lets the refresh token sit in a
`Secure; HttpOnly; SameSite=Strict` cookie scoped to `/api/v1/auth`.

## What happens when the container starts

[backend/scripts/start.sh](../backend/scripts/start.sh) runs on every deploy and restart:

1. `alembic upgrade head` applies any new migrations.
2. `python scripts/seed.py` loads the question bank. It's idempotent, so running it again changes nothing. In production it loads only questions marked `review_status: reviewed` unless `SEED_INCLUDE_DRAFTS=true`.
3. `uvicorn` serves on `$PORT` with **one worker**. The rate limiters and the model cache live in process memory. Before adding workers or instances, move them to a shared store such as Redis.

The image includes the trained model (`backend/model_artifacts/`), the shared feature code (`ml/mentorx_ml`) and the question bank. It runs as an unprivileged user.

## First deployment checklist

### 1. API and database (Render)

1. Render dashboard → **New → Blueprint** → pick this repository. Render reads `render.yaml` and creates `mentorx-api` and `mentorx-db`.
2. When prompted, fill in the variables marked `sync: false`:
   - `CORS_ORIGINS`: the Vercel URL, e.g. `https://mentorx.vercel.app`. Requests normally arrive through the same-origin rewrite, so this is a second line of defence.
   - `SEED_INCLUDE_DRAFTS`: leave it **empty**. Set it to `true` only for a supervised demo while the question bank is still awaiting review. Without it, a bank with no reviewed questions leaves the subject empty.
3. `JWT_SECRET` is generated by Render. The app refuses to start in production with the dev secret or with `COOKIE_SECURE=false`.
4. Wait for the deploy. Render polls `/api/v1/health/ready`, which checks the database and the model, before switching traffic.
5. Note the service URL. Render usually adds a suffix (ours is `https://mentorx-api-2a6a.onrender.com`). **Never guess it**: the plain `mentorx-api.onrender.com` belongs to another Render user, and pointing the rewrite there would send students' passwords to a stranger.

### 2. Frontend (Vercel)

1. Vercel → **Add New → Project** → import the repository, set **Root Directory** to `frontend`. `vercel.json` sets the framework, build and output.
2. Set the `/api/:path*` rewrite destination in `frontend/vercel.json` to your exact Render URL and commit. Then open `https://<your-app>.vercel.app/api/v1/health`: it must show `{"status":"ok"}`. Anything else means the rewrite points at the wrong server.
3. Don't set `VITE_API_URL`. Leaving it empty keeps API calls same-origin.

### 3. Smoke test production

```bash
cd backend
python scripts/smoke.py https://<your-app>.vercel.app      # through the rewrite (what users hit)
python scripts/smoke.py https://mentorx-api-2a6a.onrender.com   # the API directly
```

The script creates a throwaway account, enrols, answers one diagnostic question, reads the dashboard and the learning path, checks the security headers, HSTS and the refresh cookie round trip, then deletes the account. It exits non-zero on the first failure. Run it after every production deploy.

CI runs the same script against the freshly built Docker image (the `docker` job in [.github/workflows/ci.yml](../.github/workflows/ci.yml)). Every push to `main` is therefore checked for a working image, migrations, seeding and model loading before Render auto-deploys it.

## Environment variables

| Variable | Production value | Notes |
|---|---|---|
| `ENVIRONMENT` | `production` | Turns on the production checks, HSTS and reviewed-only seeding, and turns off `/docs` |
| `DATABASE_URL` | from `mentorx-db` | `postgres://` URLs are rewritten to the psycopg driver automatically (Render, Neon) |
| `JWT_SECRET` | generated | 32+ random characters |
| `COOKIE_SECURE` | `true` | Required in production |
| `COOKIE_SAMESITE` | `strict` | Works because of the same-origin rewrite |
| `CORS_ORIGINS` | Vercel URL | Comma-separated |
| `SEED_INCLUDE_DRAFTS` | unset | See above |
| `PILOT_ACTIVE` | `false` | `true` while pilot sign-ups are open ([pilot guide](modules/pilot.md)) |
| `POSTTEST_OPEN` | `false` | `true` at the end of the pilot |
| `ADMIN_EMAILS` | your team's emails | Comma-separated; these accounts see the Study page and exports |
| `LOG_LEVEL` | `INFO` | JSON logs with a request ID per request (the `X-Request-ID` header) |
| `LOGIN_ATTEMPTS_PER_MINUTE` | `5` | Per account |
| `REGISTRATIONS_PER_HOUR` | `10` | Per client IP |
| `EXPOSE_DOCS` | unset | `true` re-enables `/docs` in production |

## Hardening in place

- **Security headers**: on every API response (`nosniff`, `DENY` framing, `no-referrer`, a deny-all CSP, `Cache-Control: no-store` on `/api/*`, and HSTS in production), and on the frontend through `vercel.json` (a strict CSP with no inline scripts and no third-party origins).
- **Rate limits**: login attempts per account, and registrations per client IP (HTTP 429 with `Retry-After`).
- **Production config validation**: the app won't boot with the dev JWT secret or insecure cookies.
- **Smaller attack surface**: no interactive docs or OpenAPI schema in production, no `Server` header, and the container runs as a non-root user.
- **Error pages**: the frontend has a not-found route and an error boundary, and the API returns structured JSON errors with a request ID.

## Known limitations of the free plans

- **Cold starts.** Render's free web service sleeps after about 15 minutes idle, and the first request then takes up to about a minute. Vercel's rewrite may time out on that request, and a retry succeeds. Before a demo or a pilot session, open `/api/v1/health` first, or move to a paid instance.
- **Free Postgres expiry.** Render's free databases expire after a limited period (check the current Render terms). Before the pilot (M11), either upgrade the database or point `DATABASE_URL` at another managed Postgres such as Neon. The URL is normalised either way. Back up first with `pg_dump`.
- **Client IP for the registration limit.** Uvicorn trusts `X-Forwarded-For` from any proxy (`FORWARDED_ALLOW_IPS=*`), because Render's proxy addresses aren't fixed. A client calling Render directly could spoof that header to get around the per-IP sign-up limit. The per-account login limit doesn't depend on IP. This is acceptable for the pilot's scale. Revisit it with a shared limiter store.
- **Single instance.** See "What happens when the container starts".

## Load testing (NFR-PERF-01)

```bash
cd backend
REGISTRATIONS_PER_HOUR=1000 uvicorn app.main:app --port 8000
python scripts/loadtest.py http://127.0.0.1:8000 --users 50 --questions 20
```

The target is p95 ≤ 300 ms for *next question* and *submit answer*. Run it against a local server or a staging copy, not the production database.
